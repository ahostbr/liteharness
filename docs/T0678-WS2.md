# T0678-A WS2 candidate — clerk seat support, not activation

Approved private coordination plan: T0678 mail-clerk-20261024. This additive candidate follows the WS1 routing candidate and its malformed-presence fix. One builder/self-review; no critic. No app or real clerk was launched, no live fleet process killed, no merge or public push performed.

## Pain Diagnosis

Routing alone cannot safely forward decisions: the clerk needs its own registered identity, an exact-body forwarding command and auditable receipts. A launcher print, an invented `clerk_id`, or a digest saying “forwarded” is insufficient evidence that the original reached the orchestrator.

## Composition Analysis

`liteharness/clerk.py` composes the existing `cmd_spawn`, registry, atomic config writer and maildir sender. Its forward operation reuses the existing nonblocking OS lock in `mod_inbox._locked`; it neither creates another reader nor introduces a lock framework. The role is a packaged text asset, not a classifier service. Audit is a standalone stdlib script, reading actual source and forwarded files independently.

## Refactoring / delivered scope

- `clerk enable --for <orchestrator-id>` records opt-in defaults without starting a seat; `disable` stops routing without stopping the seat; `status` prints enabled/online/id/model.
- `clerk start --pane <paneId> [--cli litetui|claude-code] [--model ...] [--backend ...] [--cwd ...]` requires an explicit nonempty target pane and passes it unchanged to the existing spawn path (`split_pane`); there is no inferred/default placement. Default LiteTUI model is Astra, cognitive Aurelius, thinking high. Claude Code maps to existing internal `claude` route. A persistent offline Clerk resumes the same identity; a live Clerk is never replaced.
- Model allowlist is editable configuration. Defaults are Astra, Sol, Sonnet 5.5 and Haiku 5.5. Opus is refused by that default allowlist. Locals require an explicitly supported existing backend and allowlist entry; no model is loaded by this candidate/test execution.
- A successful start requires a unique actual live Clerk registration with the expected parent. Printed success without registration is refused. Configuration changed during spawn is not overwritten. A real launch refusal remains an explicit failure, not a fake online status.
- LiteTUI uses the existing `system_prompt_file` role replacement; Claude uses the existing prompt brief. No invented `--role-prompt-file` flag or new spawn API.
- `clerk forward <msg-id>` reads the exact original by ID from the clerk's own mail, sends a NEW message from its own ID, preserves `forwarded_for`, `reply_to` and body verbatim after the identity/FWD display lines, and appends the forwarded digest receipt.
- Concurrent forwards use the existing OS lock. Contention is a visible refusal, never a successful send. Sequential retries reuse the actual outbound receipt; if send succeeded but digest append failed, retry repairs the digest without another outbound message.
- `clerk digest <msg-id> --action ... --summary ...` records ordinary actions, capped at 140 characters. It cannot forge a `forwarded` action; only the forward helper writes that receipt.
- Audit prints `reached_sentinel`, `handled`, `forwarded`, `never_list_violations`. It exits 1 for never-list handling, missing/altered claimed forward receipts or missing identity labels. An unavailable source/delivery record is not reported as a clean day. Corrupt/unreadable inputs exit 2 with an explicit diagnostic.

## Approved extra WS2 correction — preserve every digest action

Owner review found that the first audit implementation used last-write-wins state
for an append-only decision history. With a genuine source and exact forwarded
receiver receipt, `answered` followed by `forwarded` for the SAME message ID
incorrectly exited 0 with `handled=0 forwarded=1 never_list_violations=0`.
The original green set did not cover that history; it was not evidence that a
later forward could never conceal an earlier forbidden handling decision.

The controlled subprocess regression was RED (1 failed, 26 deselected). The
approved bounded fix retains every digest row per message ID and evaluates every
action. Counts likewise count actions, not only each message's final state.
The SAME fixture now exits 1 with `reached_sentinel=1 handled=1 forwarded=1
never_list_violations=1`; targeted regression GREEN (1 passed), then focused audit
and clerk CLI tests **52 passed**. `git diff --check` clean; no unrelated formatter
changes. No routing, classifier, retention, activation or deployment changes.
